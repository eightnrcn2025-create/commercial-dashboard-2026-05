01写在前面

这份 SOP 不是"按这 30 步做就能拿到一模一样的系统"，而是 一份决策记录 + 设计模式。

读者预期：非技术 / 半技术的项目负责人，需要给团队/老板出一个数据看板，但不想找开发对接（开发太忙 / 太贵 / 太慢）。

这套方案的特点：

  • 不依赖后端开发 — 数据从现有 admin 页面"扒"，不需要 API
  • 不依赖运营商 — 全部用免费服务（GitHub / Cloudflare Workers 免费层）
  • 不依赖你电脑常开 — 跑在云上 VPS
  • 团队共享 — 公开 URL，谁都能看（也意味着数据本身公开，要权衡）

预期工期：3-5 个工作日（含调研、试错）。重做一遍熟手大约 1 天。

02需求与边界

2.1 跟需求方对齐 3 件事

  1. 核心指标是什么？（不止"我都想看" — 列前 10 个最关键的）
  2. 谁来用？（老板 / 运营团队 / 客户支持？粒度和呈现方式不一样）
  3. 需要多新？（实时 vs 每天 vs 每小时？延迟接受度决定架构复杂度）
我们这次的答案
  • 核心指标：商业化（充值、付费率、ARPU、付费分层、留存、LTV）
  • 使用者：5-10 人运营/产品团队
  • 更新延迟：30 分钟可接受（不是炒股 / 不需要秒级）

2.2 边界（明确不做什么）

  • ❌ 不做实时（< 1 分钟）— 后台数据本身就是 30 分钟批处理
  • ❌ 不做权限分级 — 团队都看同一份，没分角色
  • ❌ 不做数据二次加工 — 看板只展示，不改数（怕和后台对不上）
  • ❌ 不做移动端专门优化 — 响应式但不追求 mobile-first

明确边界很重要 — 后续有人提"能不能加 xxx"，你有依据说"超出范围，下一版再议"。

03指标体系设计

3.1 三层结构

  1. 总览大盘：5-8 个 KPI 卡，老板秒懂
  2. 分维度：游戏 / 渠道 / 套餐 / 时间……每维度一个 tab
  3. 深度分析：LTV / 留存 / 区间对比，给运营做决策用

3.2 推荐流程

a) 列指标候选 ~2h
让需求方写 50 个想看的指标，可能重复 / 冗余 / 没数据，先不评判
b) 跟后台逐项对齐 ~4h
每个指标标"后台已有 / 派生可算 / 待新建"，估出工作量分布
c) 精简到 30-50 项 ~1h
把冗余 / 边缘指标砍掉。砍 30% 通常没人不舒服
d) 输出指标 → 后台位置 映射表（CSV）
这张表是后续所有工作的"宪法" — 实现时按这个对，需求方提新指标也按这个加

3.3 经验：哪些指标"看着重要其实用得少"

指标为什么砍
人均订单数客单价 + ARPPU 能推出来
人均剩余 G 点总剩余分活跃/流失够用
登入游戏用户数跟 DAU 高度重叠
付费分层 8 档5 档（小/中/大/超/鲸鱼 R）就够

04数据抓取选型

4.1 三条路

方案优势劣势
A. 找开发要 API速度快、稳定排期可能要等几周；改 admin 时容易漏改 API
B. 直接连数据库最灵活需要 DBA 配权限；指标口径要自己重写一遍（容易和 admin 对不上）
C. 浏览器自动化扒 admin 网页不依赖任何人；口径天然和 admin 一致慢；admin 改版会挂；要处理多层登录
我们的选择

选 C（浏览器自动化）。理由："非技术运营要做一个看板"这个需求里，让 IT / 后端排期是最大风险点。C 方案完全自主，能立刻起步。

4.2 浏览器自动化工具选型

工具评价
Playwright✅ 选这个。多浏览器、headless 友好、API 现代化、社区活跃
Puppeteer只支持 Chromium，比 Playwright 稍老
Selenium太老，配置复杂
BeautifulSoup / requests纯 HTTP，但搞不定 JS 异步加载的表格

05登录认证处理

这一步是 90% 的 admin 系统都要面对的，而且通常比你想的复杂。本项目 admin1866 有 三层：

5.1 第一层：nginx Basic Auth

访问 admin URL，浏览器弹"输入用户名密码"系统级对话框。这是 HTTP 协议层面的 Basic Authentication。

// Playwright 写法：在 context 启动时塞凭证
ctx = p.chromium.launch_persistent_context(
    http_credentials={
        'username': 'xxx',
        'password': 'yyy'
    }
)
坑

很多教程只教你登录表单，没提 Basic Auth 这层。一开始登录失败时，先 curl 一下，如果返回 401 + WWW-Authenticate: Basic，就是这里。

5.2 第二层：表单登录（账号 + 密码）

过了 Basic Auth 后，是 admin 自己的登录页。常规填表 + submit。

5.3 第三层：Google Authenticator 2FA

表单还有第三个字段："谷歌验证码" — 6 位每 30 秒变。

处理方案：拿到原始 TOTP 密钥（base32 字符串，不是 6 位数字），用 pyotp 自动生成：

import pyotp
code = pyotp.TOTP(seed).now()  # 拿当前 6 位数字
page.fill('input[placeholder="请输入谷歌验证码"]', code)
如何拿到 TOTP 密钥
  • 当初扫码绑定时截图过的可以直接用
  • 没截过 → admin 里重置 2FA，新生成时把密钥截下来再扫码
  • 找当初配置 admin 的人要

5.4 凭证存哪

3 个候选，安全性递减：

  1. macOS Keychain（最安全）— 但背景服务读不了（后面会踩到）
  2. .env 文件 + chmod 600 + .gitignore（次之）— 我们最终的方案
  3. 明文写代码里（❌）— GitHub secret scanning 会拦下 push

06脚本核心实现

6.1 找出报表的真实 URL

不要手猜 URL（我们一开始猜的 7 个全错）。正确做法：

  1. 用 Playwright 登录进 admin
  2. 读 sidebar 所有 <a> 标签的 lay-href（layui 框架的路由属性）：
const links = page.evaluate(() => [...document.querySelectorAll('a[lay-href]')]
  .map(a => ({ text: a.innerText.trim(), href: a.getAttribute('lay-href') }))
);

得到 50+ 行 报表名 → URL 映射，挑你要的填到 REPORT_URLS dict 里。

6.2 抓表格通用流程

page.goto(报表 URL)
wait_for_function — 等 .layui-table-body 里有 tr
JS 改 date input 的 value + dispatch change 事件
JS 找 "搜索" 按钮 click
智能等表格行数稳定（500ms 无变化）→ 比硬等 3.5s 快
改分页 select 为 "3000/页"
智能等表格稳定
querySelectorAll('tbody tr') → 提取所有行

6.3 处理"单页 3000 行上限"

大表（比如 200 游戏 × 30 天 = 6000 行）超过单页上限，分块抓：

def fetch_report_chunked(report, start, end, chunk_days=14):
    all_rows = []
    cur = start
    while cur <= end:
        chunk_end = min(cur + timedelta(days=chunk_days - 1), end)
        rows = fetch_report(report, cur, chunk_end)
        all_rows.extend(rows)
        cur = chunk_end + timedelta(days=1)
    return all_rows

6.4 增量归档（防数据丢失）

admin 后台往往只保留 6-12 个月数据。不要依赖后台保留历史 — 每次脚本跑都把新数据 merge 到 data.js 里现有的：

def archive_merge(path, new_data):
    existing = read_existing(path)
    # 新数据按日期覆盖旧的；新里没有的，保留旧的
    merged = {**old, **new_by_date}
    return list(merged.values())

效果：哪怕后台 1 年后清掉 2025-09 数据，你 data.js 里依然有。

6.5 输出 JS 文件而不是 JSON

静态网页拿数据有两种方式：

方式优劣
fetch('data.json')需要异步加载、loading 状态、错误处理
<script src="data.js">同步加载、全局变量直接用、简单

选后者。脚本输出：

const SNAPSHOT_AT = "2026-06-03T21:05:05";

07看板前端

7.1 选型：ECharts vs 其他

方案评价
ECharts✅ 选这个。百度开源、中文文档、tooltip 默认中文化、移动端 OK、免费
Chart.js更轻量但功能少，复杂图（如桑基图）做不了
D3.js太底层，自己拼太累
Recharts / Plotly都要 React，单文件方案不合适

7.2 架构：单 HTML + 3 个 JS 文件

index.html       结构 + CSS（视觉）
data.js          数据（脚本生成、覆盖）
app.js           交互逻辑（tab 切换、图表渲染、日期对比）
config.js        Worker URL 配置（手填一次）

不用框架（React / Vue）— 单文件 + ECharts CDN 已经够用，省去 build 工具的复杂度。

7.3 视觉风格

  • 深海军蓝 header + 暗金 accent — "执行级"质感（比饱和 SaaS 蓝高级）
  • 大写英文小标题 + 中文副注 — 编辑/咨询报告风
  • tabular numerals (font-feature-settings: "tnum") — 数字等宽对齐
  • 少用饱和色 — 同色系深浅区分系列

7.4 交互必备

  1. 日期选择器：默认显示昨天（完整数据），可切到任意日
  2. 区间对比：本期 vs 对比期，预设 + 自由日期
  3. 时间区间切换：每个 tab 顶部 7天/30天/自定义
  4. tooltip 信息密度高：hover 一个点出所有相关指标
  5. 刷新按钮：强制 cache-bust，避免老旧浏览器拿缓存

08托管 / 发布

8.1 静态托管选型

方案评价
GitHub Pages✅ 选这个。免费、自动 CDN、绑域名简单、跟 Git workflow 一体
Cloudflare Pages类似，速度更快，但要单独账号
Vercel / Netlify类似，对前端框架友好但本项目用不上
自己买 VPS 跑 nginx没必要 — 看板就是几个静态文件

8.2 数据存哪

data.js 跟代码一起放仓库。GitHub Pages 服务的文件 = repo 的文件。

权衡

这意味着 数据是公开的（repo 是 public，Pages 才免费）。决策时要跟需求方说清。我们项目里数据虽然是公司商业指标，但不属于高度机密 — 接受了。

如果数据高度敏感，要么：

  • 用 Cloudflare Pages + Access（私有访问，要登录）
  • GitHub Pro（30/月，私有 repo 也能开 Pages）
  • 自己起 nginx 在 VPS 上 + 基本认证

09自动化调度

9.1 想清楚谁来跑脚本

脚本需要：

  • 能上 admin1866 的网（内网 .line.ccc 域名）
  • 能定时触发（每 30 分钟）
  • 能 git push 到 GitHub

候选机器：

  1. 你的 Mac（开机时能跑，关机就停）
  2. 云上 VPS（24×7 在线，但通常公网，访问不了内网）
  3. 公司服务器（24×7 + 在内网，但要 IT 配合）

9.2 调度工具

平台工具评价
macOSlaunchd系统原生，支持休眠唤醒
Linuxcron最普及，简单可靠
云端GitHub Actions cron免费但 runner 在公网 — 内网数据源用不上

9.3 我们的双重保险

Mac launchd（每 30 分钟）+ VPS cron（每 30 分钟）+ 团队点刷新（任意时刻） — 三种触发方式，任一在线即可。

10远程触发 + Worker

这一节是设计上最绕、但最重要的一节。

10.1 问题

团队点"刷新"按钮，希望立刻拉新数据（而不是等下次 30 分钟）。怎么让浏览器触发"在 VPS / Mac 上跑脚本"？

10.2 思路：GitHub Actions workflow_dispatch

GitHub Actions 自带"手动触发"API：

POST https://api.github.com/repos/{owner}/{repo}/actions/workflows/refresh.yml/dispatches
Headers: Authorization: Bearer <PAT>

workflow 跑在 self-hosted runner（我们的 Mac / VPS）上 — 解决了"内网访问"问题。

10.3 问题：PAT 放哪？

第一版失败的尝试

把 PAT 直接嵌入前端 config.js：

const GITHUB_PAT = 'github_pat_xxx';

结果：

  • GitHub secret scanning 自动检测，拒绝 push
  • 就算 push 成功，PAT 在 public repo 里 = 全网可见

10.4 解决：Cloudflare Worker 当中间代理

架构：

[前端] --POST--> [Cloudflare Worker] --POST + PAT--> [GitHub API] ↑ env.GITHUB_PAT (Cloudflare 加密 secret)

关键设计：

  • Worker 代码本身 不含 PAT，只读 env.GITHUB_PAT
  • PAT 用 wrangler secret put GITHUB_PAT 设入 Cloudflare 加密存储
  • 前端只调 POST https://<worker>.workers.dev/dispatch — URL 公开 OK
  • 同样的 Worker 也提供 /status 给前端轮询任务进度

10.5 为什么选 Cloudflare Worker（不是 AWS Lambda 等）

  • 免费层：100,000 请求/天，完全够用
  • 部署最简单：wrangler deploy 一行命令
  • 全球边缘，延迟低
  • 不需要绑定信用卡

10.6 Worker 代码（核心）

export default {
  async fetch(request, env) {
    const url = new URL(request.url);

    if (url.pathname === '/dispatch') {
      const res = await fetch(
        `https://api.github.com/repos/${REPO}/actions/workflows/${WORKFLOW}/dispatches`,
        {
          method: 'POST',
          headers: {
            'Authorization': `Bearer ${env.GITHUB_PAT}`,
            'Accept': 'application/vnd.github+json',
            ...
          },
          body: JSON.stringify({ ref: 'main' }),
        }
      );
      return new Response(res.status === 204 ? 'OK' : 'error', { ... });
    }
  }
};

11高可用部署

11.1 双 runner 互为备份

GitHub 允许同一 repo 注册多个 self-hosted runner。任务来时谁先空闲谁拿，自带负载均衡。

  • 主力：Hostinger VPS（Ubuntu 24.04，24×7 在线）
  • 备份：你的 Mac（开机时也接任务）

11.2 VPS 能上内网的特殊情况

幸运发现

本项目 admin1866 用的 .line.ccc 域名，居然能从公网 Hostinger VPS 访问（可能配了公网 CNAME / Anycast）。

正常情况下，公司内网域名公网不可达。如果你的项目内网完全封闭：

  • 要么找公司内一台 24×7 机器装 runner
  • 要么搞 VPN 隧道（复杂，IT 配合）
  • 要么用 Cloudflare Tunnel（IT 同意装）

11.3 workflow concurrency 防并发

Mac 和 VPS 可能同时跑（cron + workflow 撞上），都 push 会冲突。在 workflow yml 里：

concurrency:
  group: refresh-data
  cancel-in-progress: false

保证同一时间只有一个在跑，新触发的排队等。

12性能优化

12.1 优化前 vs 优化后

阶段耗时
初版（朴素实现）~3 分 30 秒
智能等待 + 智能轮询~2 分 14 秒（-35%）
更多优化的潜力~1 分 30 秒（理论）

12.2 已做的优化

  1. 智能等表格稳定：行数 500ms 无变化即继续，替代死等 3.5s
  2. 智能轮询 Pages 重建：每 2 秒 fetch data.js，发现 SNAPSHOT_AT 变了立刻 reload
  3. 合并 git pull/push：脚本里用 GITHUB_TOKEN env 走 http extraheader auth（绕开 Keychain）

12.3 还能做的

  • 消除冗余 fetch：7d 数据是 30d 子集，前端可以自己切片
  • 并行抓取：多个 Playwright 页面共享 cookie，并发抓不同报表
  • 抓取改 HTTP：跳过 Playwright，直接 httpx + 解析 HTML（要逆向 admin 接口，复杂度高）

13踩过的坑 必看

按踩到时间顺序排，每个坑后面附"什么时候你也可能踩到"。

① URL 路径全是猜的

第一版 update_data.py 我自己想 URL：/system/gameStat、/system/channelStat...跑起来全 404。

正确做法：先登进 admin，扒所有 a[lay-href] 拿到真实 URL 列表。

② nginx Basic Auth 没认出来

登录页表单填好但提交失败 — 一直以为是表单字段名错了，其实是第一层 Basic Auth 没过。

识别：curl 一下，如果返回 401 + WWW-Authenticate: Basic 就是这层。

③ TOTP 用户搞混"密钥"和"6 位数字"

非技术用户经常误以为"Google Authenticator 上的 6 位数字"就是 TOTP 密钥 — 不是。密钥是初始扫码时的那串字母数字。

④ macOS Keychain 后台读不了

第一版用 keychain 存密码，本地手动跑 OK，launchd 跑就报错 -25308（"User interaction is not allowed"）。

原因：launchd 启动的进程不在用户 UI session 里，没权限弹 keychain 解锁框。

解决：改 .env 文件 + chmod 600，gitignored。

⑤ GitHub secret scanning 拦 PAT

把 PAT 嵌入 config.js push — GitHub 自动检测出来，拒绝 push（这是好事）。

解决：用 Cloudflare Worker 代理。

⑥ Self-hosted runner 用 osxkeychain credential helper push 失败

同样的 keychain 后台访问限制，git push 也挂。

解决：workflow 里 inject secrets.GITHUB_TOKEN，脚本里：

auth = base64.b64encode(f'x-access-token:{TOKEN}'.encode()).decode()
git -c "http.extraheader=AUTHORIZATION: basic {auth}" push

⑦ Cloudflare Workers 新 UI 默认创"Static Assets"型

新版 CF UI 默认建"Worker + Static Assets"，这种 Worker 不能加 Secret。

解决：用 wrangler deploy 命令行部署 — 100% 纯 Worker。

⑧ data.js 包含 PAT 历史 — 即使删了 push 还是被拦

第一次 push 失败后改了代码再 push，还是被拦。因为 git 历史里上一个 commit 含 PAT。

解决：git rebase --onto 把含 PAT 的 commit 从历史里抹掉，force push。

⑨ admin1866 偶尔 ERR_EMPTY_RESPONSE

服务器看到 Playwright headless 流量会偶尔抽风。

解决：登录函数加 6 次重试，间隔递增 5/8/11/14/17/20 秒。

⑩ "选定日"默认显示成 6/1 而不是 6/2

按钮逻辑用 DATE_MAX - 1，但 DATE_MAX 滞后于真实日期。

解决：用浏览器 new Date() 作锚点，clamp 到数据范围内。

15复刻这套的最短路径
